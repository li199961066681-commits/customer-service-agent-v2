# 架构设计（LangGraph 状态机版）

## 1. 总体架构

本项目是一个「单 Agent、多分支」的客服工单处理系统：**LangGraph 状态机**（8 个执行节点 + 2 处条件路由）编排全部流程，LLM 负责决策，Tool 负责执行，两层存储负责记忆与持久化，Langfuse/LocalTrace 负责全链路可观测。

```
用户输入（Web UI / CLI）
        │
        ▼
┌────────────────────────────────────────────────┐
│ ① classify_intent 意图分类                      │
│    LLM 结构化输出 → {intent, confidence, slots} │
└───────────────┬────────────────────────────────┘
                ▼
┌────────────────────────────────────────────────┐
│ ② conditional_edges 条件路由                    │
│    faq → 检索 │ action → 工具 │ 模糊 → 追问      │
│    敏感/投诉 → 转人工 │ 无关 → 兜底              │
└──┬──────────┬──────────┬──────────┬────────────┘
   ▼          ▼          ▼          ▼
┌───────┐ ┌────────┐ ┌───────┐ ┌────────┐
│③RAG检索│ │④工具调用│ │⑤澄清追问│ │⑧转人工  │
└───┬───┘ └───┬────┘ └───────┘ └───┬────┘
    ▼         ▼                    │
┌────────────────────────────────┐  │
│ ⑥ escalate_check 升级判定       │◄─┘
│  层1 置信度 / 层2 self-check    │
│  / 层3 敏感词拦截               │
└───────────┬────────────────────┘
            ▼
┌───────────────────────────────┐
│ ⑦ respond 回答合成（带【资料N】）│
└───────────────┬───────────────┘
                ▼
         END（写记忆 + Trace）
```

8 个执行节点 + 2 处条件路由（条件路由不是 node）：

| # | 环节 | 职责 | 关键实现 |
| --- | --- | --- | --- |
| 1 | `classify_intent` | 判断 faq/action/clarify/human/other 五类，输出置信度 | LLM 结构化输出（Pydantic 校验） |
| 2 | `conditional_edges` | 按意图分流（条件路由，不是 node） | `add_conditional_edges` |
| 3 | `rag_search` | 知识库 Top-3 检索 + grounded 标记 | Chroma/Memory 向量库 + 阈值 |
| 4 | `tool_call` | 选工具、传参、执行 | LLM 结构化输出 + Tool 注册表 |
| 5 | `clarify` | 缺槽位（订单号）时反问 | 槽位列表 + 追问话术 |
| 6 | `respond` | 合成回答：faq 走 LLM，action 走工具结果转话术 | Prompt 护栏 + `_humanize_tool_result` |
| 7 | `escalate_check` | 三层防御升级判定 | 置信度 / self-check / 敏感词 |
| 8 | `escalate_human` | 打包上下文写坐席队列，体面转人工 | SQLite queue 表 |
| 9 | `fallback` | 闲聊/超纲礼貌引导回业务 | 固定话术 |

## 2. 数据流（AgentState）

所有节点共享同一个 Pydantic 状态对象 `AgentState`，LangGraph 在节点间自动传递增量：

```
user_input / session_id / messages
    → intent（结构化分类结果）
    → route（路由分支）
    → kb_results（检索命中）
    → tool_result（工具返回 JSON）
    → draft_reply（拟回复）
    → escalation（三层防御结论）
    → reply（最终回复）
```

**为什么要 Pydantic**：节点输出格式不合法时立即报错（fail fast），而不是带病往下传；`model_validate` 把 LangGraph 返回的 dict 还原成类型安全的状态对象。

## 3. 条件路由（决策的骨架）

LangGraph 的 `add_conditional_edges` 是「LLM 做决策 → 代码执行分流」的关键：

```python
builder.add_conditional_edges("classify_intent", route_after_classify, {
    "faq": "rag_search", "action": "tool_call",
    "clarify": "clarify", "human": "escalate_human", "other": "fallback",
})
```

`route_after_classify` 只是一个普通函数：读 state 里的意图字段，返回字符串，LangGraph 查映射表决定下一个节点。**分支逻辑是显式、可读、可测试的**——这是比「把路由写死在 Prompt 里」更工程化的做法。

## 4. 三层防御（知道自己不知道）

| 层 | 触发条件 | 动作 | 对应节点 |
| --- | --- | --- | --- |
| 层1 检索置信度 | faq 分支无 grounded 命中（相似度 < 0.25） | 拒答 → 转人工 | escalate_check |
| 层2 LLM self-check | 拟回复不带【资料N】引用 | 质检失败 → 转人工 | escalate_check |
| 层3 敏感词拦截 | 用户输入含投诉/愤怒词 | 无条件转人工 | escalate_check（所有分支） |

防御顺序：先算完（检索 + 合成草稿），再统一质检（escalate_check），最后才输出。**质检是独立节点**，不混在回答节点里——可以在不改回答逻辑的情况下单独增强防御。

## 5. 存储与观测

| 层 | 技术 | 存什么 | 降级策略 |
| --- | --- | --- | --- |
| 短期记忆 | Redis（ShortTermMemory 门面） | 最近 10 条消息，入口读入 `AgentState.messages` | 连不上自动降级进程内 dict |
| 长期存储 | SQLite（TicketStore） | 工单表 + 坐席队列表 | 零依赖内置 |
| 知识库 | Chroma + 本地词表向量（BGE-M3 接口留空） | KB 向量 + 原文 | 降级 numpy MemoryBackend |
| 观测 | Langfuse v5（OTel，工厂） | 输入/决策/工具/耗时 Trace | 降级本地 trace_log.jsonl |
